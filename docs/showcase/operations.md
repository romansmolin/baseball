# Baseball showcase operations

The showcase is disabled unless `SHOWCASE_ENABLED=true`. New Daily Lineup, Weekend Series and recurring-series publication also requires `CONTEST_PUBLISHERS_ENABLED=true`; it defaults to disabled. Existing contest pages and scoring remain available when only the publisher flag is off. Node.js 22 or newer is required by DiceBear 10.x. Runtime avatars are generated by the official DiceBear library with the CC0 Notionists style; there are no calls to the public avatar service. The application and Prisma resolve the connection in this order: `DATABASE_URL`, `STORAGE_PRISMA_DATABASE_URL`, then `STORAGE_POSTGRES_URL`. Set only the desired application connection when several URLs point to different databases.

## First installation

1. Create a dedicated PostgreSQL test database and set `TEST_DATABASE_URL` to that database, distinct from every configured application URL, for the commands below. Never use a production URL for local validation or `prisma migrate dev`.
2. Apply the generated migrations to the test database with `DATABASE_URL="$TEST_DATABASE_URL" npx prisma migrate deploy` and regenerate with `npx prisma generate`.
3. Ensure a default, valid baseball `ScoringRule` exists. On an empty disposable database the application's baseline seed can establish one. The legacy `db:seed` is destructive to its seeded tournament fixtures; do not run it against an existing showcase or production database.
4. Run `npm run showcase:seed-users -- --profiles 30000 --dry-run`. Profiles come from RandomUser 1.4 with a fixed seed. The validated import manifest is cached in git-ignored `.showcase-data/`; protect and retain this directory to reproduce exactly the same import.
5. Inspect the counts, then run `npm run showcase:seed-users -- --profiles 30000 --apply`. Existing eligible demo account IDs and all their team/league relationships are preserved. Accounts with payments, owned leagues, or privileged roles are excluded. Existing demo sessions and authentication accounts are retired, and no passwords or paid credit grants are created.
6. Run `npm run showcase:seed-history -- --days 30 --participants 1500 --dry-run`, then the same command with `--apply`. This fetches and verifies the actual July 2025 MLB statistics before publishing each replay contest. Network failures stop the import, and a rerun resumes completed days without duplicates. No fake game results are substituted.
7. To create a current-season demo leaderboard, run `npm run showcase:seed-season -- --season 2026 --days 30 --participants 1500 --dry-run`, review the source dates, game count, demo-profile coverage and positive-score count, then add `--apply`. For the application database, explicitly use `--production --dry-run` first; after reviewing the report and taking a backup, use `--production --apply`. This selects the 30 most recent verified MLB game days in that season, scores deterministic demo lineups from real box scores, and writes completed `REPLAY` contests on their original dates. It rotates participants so every active demo profile in the selected cohort receives an entry. The command is idempotent and never changes real-user entries or credit/payment data. View the results under Managers → Historical results → This season.
8. Set `SHOWCASE_ENABLED=true`. After the source and data-rights checks below, set `CONTEST_PUBLISHERS_ENABLED=true`, run `npm run showcase:tick`, and verify the new UI and API routes. Leave the publisher flag off until that review is complete.

If the seeded current-season results should populate the LIVE manager leaderboard, first inspect `npm run showcase:promote-season-live -- --season 2026 --production --dry-run`. After confirming the report has no key conflicts and contains only demo entries, add `--apply`. This changes the mode/name of those completed contests and refreshes LIVE standings; it does not duplicate entries or scores.

Commands default to `TEST_DATABASE_URL` and dry-run; writes require `--apply`. Access to the application database additionally requires `--production`. The default dataset seed is `baseball-showcase-v1`; pass `--seed` consistently to both profile and history imports when using another cohort. Reduced counts can be used for a quick isolated-database smoke test. For the current-season backfill, keep enough participants per day to cover the selected profiles across all selected game days; the command rejects a rotation that would leave profiles out.

## Updates

The daily `/api/internal/cron/showcase` endpoint requires `Authorization: Bearer <CRON_SECRET>`, using the existing project cron convention. Authenticated viewers can refresh through the same-origin `POST /api/me/showcase/refresh`. Both use a shared lease/cooldown, and callers cannot supply a simulated clock, user ID or job key. The worker has a 50-second maximum budget; calendar work is split between short-slate and recurring publishers, and an incomplete recurring source scan resumes from its stored checkpoint on the next run. The recurring score refresh runs from `/api/internal/cron/refresh-scoring` and is separately fenced by a lease.

With both flags enabled, the runner checks seven New York calendar dates for daily slates and Weekend Series. Each window needs real future games and valid rosters; a date range does not guarantee a contest. Lineups lock before the earliest included game. The publisher combines MLB Stats API games only from MLB, Triple-A and Double-A, whose box-score support is complete for contest scoring. Winter Leagues and other Latin American sources are excluded from new publication and selection; existing Winter-backed records retain their saved source and history. NPB/SPAIA stays disabled until display and redistribution rights, roster freshness and complete scoring coverage are verified; KBO is unavailable without an approved complete source. Replay is a read-only history of completed contests; the worker never copies archive games into future dates. The calendar attempt is subject to a 15-minute cooldown. Its timestamp records an attempt, not proof that every format was published. Check actual contest dates, source checkpoint and the tick's `timedOut` result. Network and database delays are visible rather than replaced with fictitious results.

Within the enabled MLB Stats API levels, `gamePk` and player IDs are MLBAM identifiers shared across those levels. Do not add a second provider to contest publication until persisted game snapshots and lineup player identities include a provider-qualified key; equal numeric IDs from unrelated providers must remain separate.

For an initial full-week publication, the calendar service can be called directly, but that write path bypasses the worker's `CONTEST_PUBLISHERS_ENABLED` gate and has no dry-run mode. Use it only against an isolated test database while validating; the normal rollout path is the gated worker. With `TEST_DATABASE_URL` set, run from the project root:

```sh
node - <<'NODE'
require('dotenv/config')
const { createJiti } = require('jiti')
const jiti = createJiti(process.cwd() + '/prisma/showcase-cli.mjs', { alias: { '@': process.cwd() + '/src' } })
;(async () => {
  const { createShowcaseCliDb } = await jiti.import('../server/services/showcase/showcase-cli-db.ts')
  const { DailyCalendarService } = await jiti.import('../server/services/daily-contests/daily-calendar.service.ts')
  const db = createShowcaseCliDb()
  try { console.log(await new DailyCalendarService(undefined, db).publishDailyContests({ now: new Date() })) }
  finally { await db.$disconnect() }
})().catch(error => { console.error(error.message); process.exitCode = 1 })
NODE
```

Do not pass `--production` to this direct call as part of rollout; use the feature-gated cron worker after staging validation. Repeated runs on the same test database keep existing contest IDs, lineups, and snapshots. Confirm the actual date range after execution; an upstream failure can leave only a partial week.

To inspect old open or locked Replay rows, run `npm run showcase:retire-open-replays -- --dry-run`. After checking the target database and taking a backup, run `npm run showcase:retire-open-replays` to mark those rows CANCELLED. This preserves their IDs, entries and events; completed history is untouched. The operation shares the `showcase:tick` lease and can be safely repeated. Dry-run is read-only and does not acquire the lease.

The profile/import scripts do not create transactions in the credit or payment ledgers. The overview distinguishes demo activity from real users. Historical result rankings remain read-only.

## Production rollout and rollback

First verify the full cohort and history on the test database. Back up the working database and preserve the import manifest; inspect a dry-run against the working database using `--production --dry-run` before applying with `--production --apply`. Use `prisma migrate deploy` for production migration, then import and enable the feature.

To stop new contest creation, set `CONTEST_PUBLISHERS_ENABLED=false`; existing results continue to be listed and scored. To disable the entire showcase, set `SHOWCASE_ENABLED=false`. Keep the additive tables and history so the feature can be re-enabled. No reset, bulk delete or backwards destructive migration is needed. Existing weekly tournaments and payment records are unaffected by disabling the showcase.
