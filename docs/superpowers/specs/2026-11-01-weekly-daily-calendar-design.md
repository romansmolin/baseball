# Недельный календарь Daily contests

Дата: 2026-11-01.
Статус: согласовано и реализовано. Во время реализации пользователь дополнительно выбрал исключение только матчей без актуальных ростеров.

## Решение пользователя

Выбран подход «Только расширить календарь до недели». Цель — показывать больше предстоящих конкурсов, публикуя сегодня и шесть следующих календарных дат. Сохраняется один Daily Classic на лигу в день.

Это увеличение доступного горизонта, а не обещание определённого количества конкурсов: даты без подходящих реальных матчей остаются пустыми.

## Что есть сейчас

- `DailyCalendarService.publishDailyContests` использует `lookaheadDays = 3`; `tickShowcase` дополнительно передаёт литерал `3`.
- Лиги: MLB, Triple-A, Double-A, Winter Leagues.
- Игровая дата определяется в `America/New_York`, время начала и блокировки сохраняется в UTC.
- Перед публикацией проверяются расписание, составы всех включённых команд и возможность собрать девять игроков в пределах 80 000.
- `classic` — ключ набора матчей; база уже обеспечивает уникальность режима, лиги, даты и ключа.
- В проверенной базе 1 ноября были три текущих конкурса Winter Leagues: за 1, 2 и 3 ноября; один закрыт для вступления, два открыты. Это снимок состояния, не прогноз недели.
- В обработчике с бюджетом 20 секунд сначала идут демоучастия/очки, затем календарь. Наличие большого объёма этой работы может лишить календарь времени; отметка `showcase:calendar.cursor.at` означает попытку, а не успешное заполнение.

## Рассмотренные подходы

1. **Недельный календарь — выбран пользователем.** Даёт больше будущих дат с действующими правилами и API.
2. Несколько наборов матчей за день. Даёт дополнительные конкурсы и дедлайны, но меняет политику формирования событий и пересечение матчей.
3. Короткие игровые форматы. Даёт разнообразие, но требует новых правил, валидации и конструктора.

## Граница первой версии

1. Горизонт — ровно 7 календарных дат: `dailyDate(now)` и смещения 1–6 в `America/New_York`. Седьмое смещение относится уже к следующему окну.
2. Тот же формат: 9 игроков, бюджет 80 000, необязательный капитан ×1.5, бесплатное участие.
3. Те же четыре источника и существующая поддержка двух сезонов для зимних лиг.
4. Существующие конкурсы, их ID, участники, снимки, сроки, составы и результаты сохраняются при повторной публикации.
5. Новые записи создаются с ключом `classic`, только по ещё не начавшимся матчам и при валидном пуле. По уточнению пользователя матчи команд, для которых отсутствует актуальный ростер, исключаются; оставшиеся реальные матчи используются, если их достаточно для валидного состава. Игроки команд из исключённых матчей не попадают в пул. Пустое расписание, отсутствие ростера и ошибки источника не заменяются вымышленными данными.
6. Каталог использует существующую пагинацию по 20 записей. При нескольких активных лигах 7-дневная выдача может занимать несколько страниц; это ожидаемо. Главная продолжает выбирать один ближайший конкурс.

## Реализация календаря

Ввести одну серверную константу `DAILY_CALENDAR_DAYS = 7` как default в сервисе. В `tickShowcase` убрать отдельное переопределение на три дня. Другие явные вызовы сервиса с меньшим горизонтом (например, unit-тесты) продолжают работать.

Проверенный частичный прогресс сохраняется существующими отдельными upsert; повторный запуск пропускает уже опубликованные даты. Перед выпуском проверить сохранение ID и записей участников на повторном запуске.

## Автоматическое обновление

Существующие cron и authenticated refresh продолжают вызывать тот же `tickShowcase`, теперь с недельным default. Сохраняются порядок фаз, бюджет 20 секунд, lease/cooldown и 15-минутный интервал между попытками календаря.

После прерывания повторная автоматическая попытка идёт по прежнему интервалу; немедленное автоматическое продолжение этот план не добавляет. Отметку попытки не использовать как доказательство полного наполнения: проверять фактические ключи и даты в БД.

Для первоначального заполнения недели допустим разовый административный вызов существующего сервиса вне общего HTTP-бюджета (см. ниже). Если проверка выявит, что существующий обработчик не успевает регулярно добавлять следующую дату недели, это отдельный подтверждённый дефект: его зафиксировать и не объявлять автоматическое обновление проверенным. Переработка очередей, курсоров и порядка фаз не входит в выбранное пользователем расширение горизонта.

## Первое заполнение и эксплуатация

Разово вызвать `new DailyCalendarService(undefined, db).publishDailyContests({ now })` из административной CLI-среды, используя существующий `createShowcaseCliDb`. Вне `withWorkDeadline` отсутствует общий 20-секундный бюджет HTTP; ограничения отдельных запросов провайдера сохраняются. Отдельная новая продуктовая CLI-команда не требуется.

По умолчанию использовать `TEST_DATABASE_URL`; база приложения допускается только с явным `--production`. Перед записью в рабочую базу прочитать существующие ключи и даты, выполнить проверку на отдельной базе и подготовить резервную копию. Новых флагов dry-run для действующего сервиса не обещать: сейчас такой режим отсутствует.

Выпуск: отдельная тестовая база → публикация недели и повтор → проверка tick на фоне незавершённых участий → чтение исходного состояния базы приложения → резервная копия → разовая публикация недели → проверка текущего каталога и главной.

## Ограничения и риски

- Подготовленный заранее пул игроков остаётся снимком на момент публикации, как в текущем Daily Classic. Этот план не вводит новую политику обновления уже опубликованных составов/дедлайнов.
- Больше опубликованных дат означает больше будущей работы, но демоучастия по прежним правилам появляются в течение 12 часов до старта. Не обещать заполненные участниками конкурсы за неделю до матча.
- Точные сроки и количество событий зависят от данных провайдера. Семь дат не означают семь гарантированных конкурсов на лигу.

## Критерии готовности

- Подходящий матч в шестом смещении публикуется; матч только в седьмом — нет.
- DST, поздний UTC-матч и переход года не меняют принадлежность игровому дню.
- Повторный и конкурентный вызовы не создают второй конкурс с тем же ключом и не меняют ID/участия существующего.
- Недоступные ростеры и статистика не превращаются в вымышленные события.
- После прерванного вызова уже созданные даты сохраняются; повтор не дублирует их.
- При проверке tick зафиксированы фактически опубликованные даты и `timedOut`; одного обновления курсора недостаточно для положительного результата.
- На тестовой базе видны подходящие даты всей недели; на главной остаётся ближайший конкурс, полный список доступен в Daily contests.

## Проверка дизайна

Независимый builder-check запросил уточнение объёма и поведения после таймаута. Решение автора в пределах выбора пользователя: исключить отдельный CLI, новые отчёты, кэш ростеров и переработку фаз; оставить существующий интервал автоматического повтора. Эти технические предложения не считаются согласованными пользователем.
