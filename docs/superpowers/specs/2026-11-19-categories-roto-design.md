# Конструктор по форматам, этап 2: H2H Categories и Roto — дизайн

Продолжает `2026-11-19-format-builder-design.md` (этап 1: H2H Points). Здесь только то, что меняется.

## Зачем
В категорийных форматах результат определяется не суммой очков, а сравнением по каждой категории (H2H Categories — с соперником за неделю, Roto — со всей лигой за сезон). Конструктор должен показывать вклад игрока по категориям и подбирать состав, который закрывает слабые категории.

## Цели
- Форматы **H2H Categories** и **Roto** выбираются и работают (пул, ручной подбор, Generate with AI, сохранение, восстановление).
- Набор категорий по умолчанию 5x5, каждую можно включить или выключить: Hitting R, HR, RBI, SB, AVG; Pitching W, SV, K, ERA, WHIP.
- Прогноз по категориям на выбранный период; Roto всегда на сезонном горизонте.
- Один и тот же игрок ранжируется по-разному в Points и Categories.
- Generate with AI сохраняет закреплённых игроков и подбирает остальных так, чтобы закрыть слабые категории; невозможный подбор объясняется причиной (как в этапе 1).

## Не цели
- Пользовательские формулы категорий и свои наборы вне списка выше.
- Таблица лиги и «сколько мест выиграем в Roto»: таблицы в продукте нет. Roto = сезонный горизонт плюс баланс категорий.
- Прогноз по конкретному сопернику в H2H.
- DFS (этап 3).

## Дизайн
- **Данные:** `FantasyTeam.categories` Json (`[]` = все 10 по умолчанию). Формат хранится уже в `format`. Для Roto период принудительно `SEASON`.
- **Прогноз:** сервис прогнозов отдаёт не только очки, но и компоненты `ProjectedStats` (r, hr, rbi, sb, ab, h, w, sv, k, ip, er, bbh = walks + hits allowed). Счётные категории считаются как ставка на игру × ожидаемые игры; AVG, ERA, WHIP считаются по сумме компонентов состава.
- **Ценность игрока:** z-оценка относительно пула прогноза. Счётная: `(x − mean) / sd` среди игроков своей стороны (hitting/pitching); другая сторона даёт 0. Ставочная (AVG, ERA, WHIP) считается по вкладу с учётом объёма: `h − poolAvg·ab`, `−(er − poolEra/9·ip)`, `−(bbh − poolWhip·ip)`, делённому на sd этих вкладов. Среднее и sd приходят вместе с прогнозами (`scales`), клиент и AI используют одни и те же.
- **Вес категории:** `1 + clamp(−среднее z состава в категории, 0, 1.5)`: чем слабее состав в категории, тем выше вес (если в команде мало SB, игроки с SB поднимаются).
- **Оценка игрока:** `Σ вес·z` по включённым категориям.
- **Generate with AI:** тот же оптимизатор, целевая функция — оценка игрока. До 3 проходов: веса считаются по закреплённым и уже выбранным игрокам; берётся проход с лучшим `teamBalance = Σ sign(S)·√|S|` по суммам z-оценок категорий (убывающая отдача, чтобы не перекашивало в одну категорию). Модель, как и раньше, только объясняет.
- **UI:** формат-пикер включает Categories и Roto; в настройках вместо правил очков чекбоксы категорий; для Roto период скрыт («Season»). В пуле — чипы лучших категорий игрока и сортировка по оценке; в мерке — итоги состава по категориям (AVG/ERA/WHIP — агрегат). В превью AI — оценка (score), не очки.

## Подходы
1. **z-оценки с весами нужды и общий оптимизатор** (выбран): один механизм для Categories и Roto, детерминированно, модель только объясняет.
2. Перебор составов под целевое число выигранных категорий против среднего соперника: требует модели соперника, которой нет.
3. Оценка категорий моделью: недетерминированно, поломка валидности. Отклонён (как в этапе 1).

## На усмотрение исполнителя
- Если категория не включает ни одной категории одной из сторон, игроки этой стороны получают оценку 0 и добираются оптимизатором на оставшиеся слоты; это допустимо, в UI подсказка.
- Метки и порядок чипов категорий.
