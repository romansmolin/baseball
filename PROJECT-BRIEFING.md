# Бриф по проекту — платформа фэнтези-бейсбола

Подготовлено для передачи агенту-оценщику. Кратко описывает текущую архитектуру
и технический контекст четырёх запрошенных изменений.

---

## 1. Стек и архитектура

| Область | Выбор |
|---|---|
| Фреймворк | Next.js 16 (App Router), React 19 |
| Язык | TypeScript |
| Архитектура | Feature-Sliced Design (FSD), без слоя `processes` |
| Состояние / данные | Zustand, SWR (+ отдельные фетчеры, обёрнутые в `withErrorHandling`) |
| БД | PostgreSQL через Prisma 7, клиент генерируется в `src/generated/prisma/` |
| Авторизация | better-auth (таблицы Session / Account / Verification) |
| Стили | Tailwind 4, UI-кит в стиле shadcn в `src/shared/ui` |
| Тесты | Vitest |
| AI-фичи | OpenAI Responses API (`server/services/ai`) — оптимизатор состава, анализ игрока, советник по трейдам, предсказатель матчапов, автозаполнение состава; оплата в кредитах |
| Платежи | Внешний шлюз («Secure Processor»), покупка пакетов кредитов, двойная запись в реестре кредитов (`CreditTransaction`, без колонки баланса) |
| Деплой | Vercel (3 крон-задачи в `vercel.json`) |

Слоистость сервера: route handler → controller → service → repository. Route
handlers владеют парсингом HTTP; Zod-схемы лежат в `server/entities/{entity}/`.
Полные правила — в `CLAUDE.md` и `docs/`.

## 2. Провайдер спортивных данных — текущее состояние

**Только один провайдер: публичный MLB Stats API** (`https://statsapi.mlb.com/api/v1`,
без API-ключа). Код в `server/providers/mlb/`.

- Абстракция провайдера: `ISportsProvider` (`server/providers/sports-provider.interface.ts`)
  - `getTeams`, `getTeamById`, `getPlayers`, `getPlayerById`, `getPlayersByTeam`,
    `getSchedule`, `getBoxScore`
- Фабрика `getSportsProvider()` переключается по env-переменной `SPORTS_PROVIDER` —
  реализован только `mlb`.
- `server/providers/api-sports/` существует с пустыми подпапками `types/` и
  `mappers/` — **брошенная/запланированная интеграция api-sports.io**. Комментарии
  в схеме и живая политика приватности всё ещё называют «api-sports.io» источником
  данных.
- Провайдер-агностичные DTO уже определены: `ProviderPlayer` (био, позиция,
  команда, фото, bats/throws), `ProviderScheduledGame`, `ProviderBoxScore`
  (`ProviderBatterLine` + `ProviderPitcherLine` — hits, doubles, triples, HR, RBI,
  runs, SB, BB, K / IP, K, ER, W).

**Хранение игроков:** таблицы **`Player` нет**. Реальные игроки ссылаются по
`externalPlayerId` — сейчас это **`Int`**, равный MLB `personId`. Строки состава
(`RosterSlot`, `WeeklyLineupSlot`) замораживают `playerName / playerPosition /
playerTeamName / playerPhotoUrl` в момент лока состава, чтобы исторические недели
рендерились и считались без повторных запросов к провайдеру.

**Подсчёт очков:** `server/services/scoring` читает замороженные снапшоты
`WeeklyLineup` + постматчевые строки `ProviderBoxScore`, применяет
версионированное `ScoringRule` (JSON-конфиг, засеяно правило «standard» v1).
Запускается лениво при просмотре standings или через крон `refresh-scoring`.

## 3. Турниры — текущее состояние

«Турнир» **— это строка в таблице `League`** (`prisma/schema/league.prisma`).
Ключевые поля: `leagueSlug` (mlb / milb / npb / …), `externalSeasonId`
(**захардкожен `2026`** в сиде), `status` (DRAFTING / IN_SEASON / PLAYOFFS /
COMPLETED / ARCHIVED), `startsAt` / `endsAt` / `totalWeeks`, `entryFeeCredits`,
`prizePoolCredits`, `visibility`.

- `currentWeek` вычисляется на сервере, не хранится.
- **Нет admin/API-пути создания турниров.** `POST /api/tournaments` не существует —
  каталог только на чтение. Турниры создаются **только через `prisma/seed.ts`**.
- Сид создаёт **4 турнира MLB** (invite-коды с префиксом `SEED-`): один COMPLETED,
  два DRAFTING, один IN_SEASON.
- Реальные данные есть **только у MLB**. Комментарии в `SEED_TOURNAMENTS` говорят,
  что турниры MiLB / NPB были намеренно удалены, потому что «реальные данные по
  игрокам есть только у MLB».

**Остальные лиги (MiLB, NPB, KBO, LVBP, LMB):**
- Перечислены в `server/shared/sport-leagues.const.ts`,
  `src/widgets/leagues/model/mock-data.ts` и селекторе лиги в team-builder.
- `LEAGUE_TEAM_GROUPS` (`src/shared/team-builder/league-teams.ts`) мапит только
  `mlb`. Всё остальное рендерится как **«Coming soon»** с пустым списком команд.
- Лендинг рекламирует «MLB · NPB · KBO · LVBP and more».

**Мок-поверхности (выглядят реально, но не реальны):**
- Страница `/leagues` — 100% мок (`src/widgets/leagues/model/mock-data.ts`):
  фейковые призовые («$240K»), фейковый `openTournaments: 128`, фейковые топ-скореры.
- Страница `/players` — 100% мок (`src/widgets/players/model/mock-data.ts`).
  Реальный роут `GET /api/players` существует (на MLB-провайдере), но UI страницы
  игроков его **не** вызывает. Реальный API игроков дёргает только автозаполнение
  в team-builder.
- Метрики дашборда / лента активности / онбординг — `server/shared/dashboard-stubs.ts`.

**Сид-юзеры:** ~49 участников, email `*@seed.local`, `passwordHash: null`,
`provider: 'seed'`. Каждый сид-юзер = 1 `User` + 1 `FantasyTeam` + 1 `LeagueMember`
+ строки `WeeklyLineup` за каждую прошедшую неделю. Составы берутся детерминированно
из захардкоженного пула 36 игроков MLB. Сид на каждом прогоне вайпает и заново
создаёт всех `@seed.local`-юзеров. Пулы имён: 30 имён × 30 фамилий.

## 4. Четыре запрошенных изменения — технический контекст

### 4a. «Больше турниров — нужно подключить ещё один id»

- Добавление **строк** турниров тривиально (расширить `SEED_TOURNAMENTS` или
  сделать admin/seed-путь). Блокер — **данные за ними**.
- «Ещё один id» скорее всего значит либо новый `externalSeasonId`, либо
  идентификатор лиги в источнике данных для не-MLB лиги.
- MLB Stats API может дотянуться до **MiLB** через другие значения `sportId`
  (11 = AAA, 12 = AA, 13 = A+, 14 = A, 16 = Rookie, 17 = зимние лиги) — тот же API,
  минимум работы.
- **NPB, KBO, LVBP, LMB в MLB Stats API отсутствуют полностью.** Для них нужен
  другой провайдер — это и есть драйвер пункта 4b.
- Вопрос к оценщику: у пользователя уже есть конкретный вендор/id лиги, или задача
  «разобраться с источником данных»?

### 4b. «Новый API должен также вытаскивать инфу об игроках — бейсбольный API не подходит»

- «Бейсбольный API» скорее всего = **API-Baseball (api-sports.io / RapidAPI)** —
  наполовину собранная интеграция, уже в репозитории. Покрывает много лиг по
  числовому `league` id + `season`, **но покрытие игроков/статистики слабое**:
  таблицы, расписание, счёт матчей, коэффициенты — нет надёжных постматчевых строк
  по игрокам, которые нужны движку подсчёта очков. Отсюда «не подходит».
- Требование: **один API, дающий и то и другое** — (a) данные расписания/турниров
  по нескольким лигам и (b) составы + постматчевую статистику по игрокам (H, 2B,
  3B, HR, RBI, R, SB, BB, K / IP, K, ER, W) под существующую форму `ProviderBoxScore`.
- Вендоры для оценки на мультилигу + статистику по игрокам: SportsDataIO,
  Sportradar Baseball, Stats Perform / Opta, Rotowire. **Покрытие NPB/KBO по
  игрокам — самое сложное**; мало у кого есть, возможно нужен отдельный источник
  под конкретную лигу.
- **Поверхность интеграции мала и уже абстрагирована:** реализовать
  `ISportsProvider` для нового вендора, зарегистрировать в
  `sports-provider.factory.ts`, добавить мапперы в `server/providers/<vendor>/`.
- **Риск волны — `externalPlayerId` это `Int` (MLB personId).** Новый вендор со
  строковыми id или другим пространством id заставит делать миграцию схемы
  (`Int` → `String`) по `RosterSlot`, `WeeklyLineupSlot`,
  `FantasyTeam.captainExternalPlayerId`, JSON `WeeklyScoreCache.breakdown` и схемам
  AI-фич. Нетривиально.
- Также завязано на вендора: enum `Position`, пространство id команд, URL фото,
  схема ключей кэша `ApiCacheEntry`.

### 4c. «Добавить 30 000 фейковых пользователей»

- Текущий сид (~49 юзеров) жёстко завязан на регистрацию в турнирах и вайпает сам
  себя каждый прогон — не основа для 30к.
- **Ключевое решение:** 30к должны просто *существовать* (строки `User` под
  счётчик вроде «12 480 менеджеров») или *участвовать* в турнирах (глубина
  standings, пулы соперников)? Регистрация 30к × составы × недельные лайнапы =
  миллионы строк → стоимость крона подсчёта и запросов standings взлетает.
- **С логином или только для отображения?** better-auth нужна строка `Account` +
  хэш пароля на юзера для реального логина; для отображения хватит голой строки
  `User`.
- Нужен **отдельный батчевый генератор** (`createMany`, чанками), идемпотентный,
  под флагом — не часть `prisma/seed.ts`. Вайп+пересоздание 30к каждый прогон
  слишком медленно.
- Ограничения уникальности: `User.email` unique, `User.username` unique. Пулы имён
  надо расширять (сейчас 900 комбинаций) или использовать числовые суффиксы.
- **Не техническое:** политика приватности и условия уже опубликованы. 30к
  синтетических аккаунтов с фейковыми PII — это бизнес/комплаенс-решение,
  вынести пользователю.

### 4d. «Видимость рабочего продукта»

Разрывы между «выглядит готовым» и «готово»:
- Страницы `/players` и `/leagues` — мок-данные с придуманными числами.
- 5 из 6 лиг — заглушки «Coming soon», при этом рекламируются на лендинге.
- Счётчики дашборда, лента активности и онбординг — заглушки.
- Подсчёт очков наполняется только если запущен крон или открыты standings (сид
  его пропускает).

«Видимость рабочего продукта» = сделать так, чтобы наполненные поверхности
(каталог турниров, standings, список игроков, счётчики дашборда) отражали реальные
или реалистично-консистентные данные от нового провайдера, и либо выпустить, либо
явно закрыть лиги «Coming soon».

## 5. Ограничения, которые обязана соблюдать любая реализация (из `CLAUDE.md` / `docs/`)

- Слоистость FSD; импорт только из `index.ts` слайса; слои импортируют только вниз.
- Никаких fetch/эффектов в UI-компонентах. Фетчеры отдельные, обёрнуты в
  `withErrorHandling`. Мапперы конвертируют DTO ↔ доменная модель на границе;
  сырые DTO-формы никогда не доходят до хуков или UI.
- Сервер: route handlers парсят `request.json()`, контроллеры — никогда. GET/DELETE
  хендлеры передают только примитивы. Zod-схемы в `server/entities`, никогда в
  контроллерах. Явные объявления свойств классов (без сокращения
  parameter-property). Вырезать `passwordHash` из каждого ответа.
- **Каждое изменение `prisma/schema/*.prisma` → `npx prisma migrate dev --name <описание>`**
  из корня проекта. Никогда `prisma db push`. Никогда не править миграции руками.
- Именование: файлы `kebab-case`, `{entity}.api.ts` / `{entity}.service.ts` /
  `{entity}.schema.ts` / `{entity}.const.ts`.

4. Есть ли бюджет на платного мультилиг-вендора спортивных данных?
5. Нужна ли регистрация фейк-юзеров в standings турниров, или хватает заголовочного
